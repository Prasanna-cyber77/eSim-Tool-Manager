# eSim Automated Tool Manager architecture

## Scope and reference

FOSSEE IIT Bombay Winter Internship 2026, eSim Screening Task 5. The proposed prototype is a standalone Python CLI for Windows 11 x64, with Ubuntu 24.04 and 26.04 LTS as the second target. The initial installation and version-checking demo uses system KiCad. The same CLI inventories eSim-owned tools, discovers an eSim root, prepares a process-scoped environment, executes one trusted analog fixture with the selected Ngspice, and reports whether the selected dependencies are usable for each eSim workflow. The manager uses the existing Python 3.13 virtual environment. The inspected Windows eSim build pins a separate, private Python 3.12.10 runtime.

Findings are from the local eSim 2.6 checkout at `d86c1891b4e1aced7ce84b910d6fba17025bd87c`. The checkout supplied source and packaging recipes without a staged Windows `tools` tree. Runtime behavior and installer outcomes remain to be tested on installed builds. [Reference revision](https://github.com/FOSSEE/eSim/tree/d86c1891b4e1aced7ce84b910d6fba17025bd87c)

## Executable discovery in eSim

### Windows launcher environment

These are PATH prefixes in search order. `custom bin` and `code-model dir` are `tools/nghdl/install_dir/bin` and `tools/nghdl/install_dir/lib/ngspice`. `stock bin` is `tools/ngspice/bin`. Bundled and system KiCad bins qualify when they contain `eeschema.exe`. The custom entries require `custom bin/ngspice.exe`.

| Entry point | Effective PATH prefix before the inherited PATH |
| --- | --- |
| Direct `Application.py` via `launcher_windows.py` | Bundled `tools/kicad/bin`, then `%ProgramFiles%/KiCad/*/bin` in reverse lexicographic order, then code-model dir, custom bin, stock bin. Prepends existing directories only. |
| `windows/esim.bat` | Bundled KiCad, then system KiCad in reverse batch enumeration order, then custom bin, code-model dir, stock bin. The stock path is added unconditionally. |
| Installed `eSim.exe` via `windows/launcher/esim_launcher.c` | Bundled KiCad, then system KiCad in Win32 enumeration order, then custom bin and stock bin. The native launcher does not add the code-model dir here. Inno Setup points the installed shortcuts to this executable. |

All three set `ESIM_ENV_READY=1` and, when the custom executable exists, set `SPICE_LIB_DIR` to `tools/nghdl/install_dir/share/ngspice`. Any nonempty inherited `ESIM_ENV_READY` skips the Python setup. The batch and native launchers set their own environment before Python starts. The order of system KiCad candidates depends on the launcher and carries no semantic version guarantee. At co-simulation runtime `NgspiceWidget` prepends the resolved code-model dir on Windows and the Icarus library dir to the child loader path. The loader variable is `PATH` on Windows and `LD_LIBRARY_PATH` on Ubuntu. The Windows simulator child can also receive MSYS2 paths for NGHDL's `mintty` and `bash`.

On Windows, `Application.py` calls `run_bootstrap()` before handling `--doctor`. This can write `~/.esim`, `~/.nghdl/config.ini`, KiCad symbol registrations, and relocate code-model paths in `spinit`. The manager's diagnostic will model resolution using read-only inputs. The installed native shortcut is the default projection for a Windows installed root. A source checkout defaults to direct Python. The CLI can select batch, direct Python, native, or inherited environment explicitly and reports which projection it used. Where multiple system KiCad versions compete under native or batch launches, mark the prediction ambiguous unless launch order is known. [Windows launcher](https://github.com/FOSSEE/eSim/blob/d86c1891b4e1aced7ce84b910d6fba17025bd87c/src/frontEnd/launcher_windows.py)

### Tool-specific resolution

Paths below are relative to the eSim root unless specified. The canonical user configuration in this revision is `~/.nghdl/config.ini` on both platforms. `NGHDL_HOME` and `RELEASE` are INI keys under `[NGHDL]`. `MSYS_HOME` is an INI key under `[COMPILER]`. Preserve INI interpolation when reading fields such as `%(NGHDL_HOME)s/release`.

| Tool | Lookup priority and probe |
| --- | --- |
| Console ngspice | Existing file from `ESIM_NGSPICE`, then `[NGHDL] NGHDL_HOME/install_dir/bin/ngspice[.exe]`, then `shutil.which('ngspice')` on effective PATH, then literal `ngspice` as the runtime fallback. The eSim doctor requires a file and probes `--version` with preference for an ngspice banner line. Treat an unresolved literal as missing. |
| ngspice plotting GUI | Windows only. Existing `ESIM_NGSPICE_GUI`, then `bin/ngspice_gui.exe` in the real prefix of the resolved console executable. Record presence separately. eSim uses the console build for captured simulation output and the `--with-wingui` twin for interactive plots. |
| KiCad editor and netlister | The editor launches `eeschema` through the launcher environment. `_kicad_cli()` takes any nonempty `ESIM_KICAD_CLI` before `shutil.which('kicad-cli')`. A bad override can stop export because the resolver does not fall back after a launch error. The manager proposes `kicad-cli version` for version detection. Probe the editor's presence independently. [KiCad CLI reference](https://docs.kicad.org/9.0/en/cli/cli.html#version-commands) |
| Icarus compiler | Existing `ESIM_IVERILOG`, then existing `[COSIM] IVERILOG`, then `library/bin/iverilog/bin/iverilog[.exe]`, then PATH, then Windows defaults under `C:/Program Files/iverilog/bin`, `C:/Program Files (x86)/iverilog/bin`, and `C:/iverilog/bin` in that order. Probe `-V`. |
| Icarus runtime | Existing `ESIM_VVP`, then existing `[COSIM] VVP`, then `vvp` beside the selected `iverilog`, then the bundled, PATH, and Windows-default searches. Probe `-V` with the Icarus loader environment. |
| Icarus shared library | Existing directory from `ESIM_IVERILOG_LIB`, then `[COSIM] IVERILOG_LIB`, then the real compiler prefix. Probe `bin` before `lib` on Windows and `lib` on Ubuntu for `libvvp*` or `vvp.dll`. An explicit existing directory can still lack the library. The resolver can return an existing `lib` as a diagnostic fallback. |
| HDL build tools | `ToolchainCheck.py` searches `<MSYS_HOME>/mingw64/bin` then PATH on Windows, and PATH on Ubuntu. Tools include `mingw32-make` on Windows or `make` on Ubuntu, `gcc`, `verilator` (Windows also tries `verilator_bin` after both locations for `verilator`), and `ghdl`. Probe `--version`. Windows checks for `<MSYS_HOME>/usr/bin/{bash,mintty}.exe` independently. |

`ToolchainCheck._run_version()` merges stderr into stdout, times out after 10 seconds, and generally returns the first nonempty line even when the process returns a nonzero exit code. The manager captures both streams and scans for a tool-specific banner after handling ANSI color codes and a byte order mark. It reports timeouts, nonzero exits, unrecognized banners and recognized prereleases. GHDL backend text can appear later in the output and is checked independently. NGHDL elaboration passes linker flags via `ghdl -e -Wl,...`, which mcode cannot handle. The Ubuntu installer checks compilation because even the LLVM driver can print a version when its compiler cannot start. The NgVeri build recipe targets Verilator 5 or newer. [eSim doctor](https://github.com/FOSSEE/eSim/blob/d86c1891b4e1aced7ce84b910d6fba17025bd87c/src/maker/ToolchainCheck.py)

Version probes use fixed arguments, closed stdin, captured streams and a ten-second timeout. `eeschema` and `ngspice-gui` receive presence checks. Known graphical names are rejected as version-probe overrides. On Windows, the manager checks the executable's PE console subsystem before probing, including for ngspice named `ngspice.exe`. The documented `kicad-cli.exe version` entry point is allowed because KiCad builds that CLI with the GUI subsystem in some Windows configurations. Paths supplied through overrides must refer to trusted binaries that implement the tool's documented command-line behavior. [Windows PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format), [KiCad 9 build rules](https://gitlab.com/kicad/code/kicad/-/blob/9.0/kicad/CMakeLists.txt), [KiCad CLI version command](https://docs.kicad.org/9.0/en/cli/cli.html#version-commands)

KiCad netlisting depends on KiCad 7+ and uses `sch export netlist --format kicadxml`. The native SPICE export can omit eSim symbol connectivity. `KicadNetlister.py` translates the XML and preserves the existing `.cir` on a missing CLI, failed export, or empty schematic. The Windows build pins KiCad 9.0.3 and packages a pruned copy under `tools/kicad`. A system WinGet install can coexist while eSim still uses the bundled copy. The Ubuntu 24.04 installer targets KiCad 9 via the eSim recipe's PPA and can fall back to Ubuntu's KiCad 7. The 26.04 profile targets KiCad 9 from Universe. Report the netlister minimum and the installer target independently. [Ubuntu 24.04 package](https://packages.ubuntu.com/noble/kicad), [Ubuntu 26.04 package](https://packages.ubuntu.com/resolute/kicad)

## Standard ngspice and eSim co-simulation

- Windows stages an official 64-bit ngspice 45.2 build with XSPICE under `tools/ngspice`. When the build uses `-SkipSimBuild`, it can copy that same stock tree into `tools/nghdl/install_dir` as a compatibility shim and stage prebuilt Bleyer Icarus for the Verilog Verifier. Path and banner alone cannot identify the custom build. The `Full` installer type enables the MSYS2 HDL component and ships the source and build trees. Compact omits these build assets and can still contain the staged simulator binaries. Report actual files and capabilities.
- The specialized `nghdl-simulator` uses a 45.2 base with eSim's NGHDL/NgVeri changes and XSPICE enabled. Both build recipes apply the checked-in patch for `d_cosim` operating-point behavior. For `d_cosim`, verify `digital.cm`, `ivlng.dll` (Windows) or `ivlng.so` (Ubuntu), `ivlng.vpi`, and the matched Icarus compiler/runtime plus loadable `libvvp`. Both build recipes pin the same Icarus source commit and use `--enable-libvvp`. The eSim diagnostic cites ngspice 44 as its minimum guidance. Build features and a smoke test carry more evidence than the version floor.
- NGHDL VHDL additionally uses `ghdl.cm`, GHDL with a working LLVM or GCC backend and the configured build tree at `[NGHDL] RELEASE/src/xspice/icm`. Legacy NgVeri uses the Verilator/compiler build chain and `Ngveri.cm` for runtime. Report each flow independently so missing HDL dependencies leave the Verilog Verifier and standalone analog capability intelligible.
- Ubuntu's eSim installer builds the custom simulator under `~/nghdl-simulator`, records its prefix in `~/.nghdl/config.ini`, and replaces `/usr/bin/ngspice` with a symlink after purging the distro package. Follow symlinks to derive the code-model prefix. System `ngspice` package operations on a host with an eSim-linked `/usr/bin/ngspice` may affect the active simulator. The prototype manages system KiCad on Windows. Specialized simulator provisioning and repair stay with eSim. [eSim patch notes](https://github.com/FOSSEE/eSim/blob/d86c1891b4e1aced7ce84b910d6fba17025bd87c/patches/ngspice/README.md), [Ubuntu NGHDL recipe](https://github.com/FOSSEE/eSim/blob/d86c1891b4e1aced7ce84b910d6fba17025bd87c/nghdl/install-nghdl.sh)

## Root discovery and process-scoped configuration

`discover_root()` applies a deterministic precedence: an explicit `--esim-root`, the manager setting, `ESIM_HOME`, the current working directory, unambiguous sibling directories near the working directory or tool-manager project (bounded to two parent levels), and the documented Windows `%SystemDrive%\FOSSEE\eSim` fallback. A candidate is accepted only when it contains `VERSION` and `src/frontEnd/Application.py`. Multiple valid sibling candidates produce an ambiguity warning and no automatic selection, so the user must choose with `--esim-root`. Selected paths are canonicalized. The older `find_root()` helper remains as a path-only wrapper.

The `env` command builds a copy of the current environment for a child process. It sets `ESIM_NGSPICE` to the selected console executable, prepends that executable's directory to `PATH` when absent, and fills `SPICE_LIB_DIR` from `<prefix>/share/ngspice` only when unset. Existing unrelated variables are preserved; an existing different `SPICE_LIB_DIR` is left intact and reported. It emits an idempotent snippet for PowerShell, cmd, or bash. `env --apply` probes an isolated child process. No parent-shell, user PATH, registry, or eSim configuration changes are made.

## CLI and internal interfaces

Use `argparse`, `pathlib`, `configparser`, `subprocess`, `logging`, and small typed records. Run with `python -m esim_tool_manager`. Use a tool catalog to hold probe arguments, version parser, capability rules, supported platform and package binding. Use distinct records for executable candidates, probe results, package metadata, and change plans. Keep package version and executable version separate.

| Component | Responsibility |
| --- | --- |
| `cli` | `list` for local inventory, `version TOOL` for targeted probes, `doctor [--flow FLOW]` for health, `env` for a preview or process-scoped simulator environment, `verify ngspice` for an isolated analog run, `validate` for the end-to-end checks, `config show/set` for manager-owned values, `updates` for available compatible upgrades, `install TOOL` and `upgrade TOOL` for plans. Install and upgrade default to preview. `--apply` displays the plan and requests interactive confirmation for one exact action. |
| `discovery` and `probes` | Build the effective search context from root, INI, launcher and environment. Return the winning path, origin, shadowed candidates and invalid inputs. Probe resolved paths with argv lists, controlled child environment, timeouts and no shell. Start no GUI for version checks. |
| `health` | Evaluate basic netlisting, analog simulation, Verilog Verifier, Icarus `d_cosim`, legacy NgVeri and NGHDL separately. `--flow` selects the tool probes and prerequisite checks for that workflow. Each workflow has a prerequisite `status` and a separate `compatibility` verdict. Version requirements can be `verified`, and known mismatches such as mcode are `incompatible`. Analog runtime compatibility is `verified` only when a valid simulation receipt matches the selected executable path, SHA-256, version, circuit and numeric result. A managed executable is classified as standard even when reached through `ESIM_NGSPICE`. Co-simulation, NGHDL, NgVeri and full GUI integration stay `unverified` until separately executed. |
| `packages` and `portable` | System KiCad uses WinGet or APT with exact package and version checks. Windows Ngspice uses a reviewed official `.7z` archive with a pinned, independently corroborated digest. Both paths preview first and recheck the plan after approval. |
| `diagnostics` | Read native WinGet integrity failures or manager failure events, including rotated manager logs. Report the selected version, source, URL, expected and actual hash and byte size when recorded. The diagnostic command invokes no subprocess and writes no logs. |
| `config` and reporting | `--esim-root` overrides manager config and then root discovery. Store settings and rotating operation logs under `%LOCALAPPDATA%/eSimToolManager` or the Ubuntu XDG config and state directories with their standard home fallbacks. Use manager-owned atomic config writes. Preview supported eSim overrides for a child process and show inferred loader settings. Persistent PATH, eSim INI and KiCad config remain read-only. Reports provide human-readable output and `--json` for automation. |

The upstream doctor tags Windows `mintty` against both simulation and NGHDL. The manager reports it with NGHDL and keeps analog simulation focused on ngspice. It flags a mixed compiler/runtime pair or mismatched `SPICE_LIB_DIR` and executable prefix. Text reports group dependencies by workflow and show the selected path and version with remediation for failed checks. Verbose mode expands searched paths, alternate candidates and version banners. JSON retains these details in structured fields. JSON Lines logs track actions, selected versions, verification and a bounded excerpt of available failure output. If a transaction errors, the manager re-queries the observed package version.

The package catalog maps platform to package ID. WinGet selects the live latest release by default and supports explicit version requests. The latest catalog version, installed package version and selected compatible target are separate fields. The KiCad 7–10 compatibility gate comes from the reference netlister and does not establish end-to-end support for a specific patch release.

The apply invocation constructs and displays its own plan, asks for confirmation, and compares the executable plan again immediately before invoking the exact package command. WinGet plan equality covers package ID, scope and architecture in the command, installed and target versions, installer URL and SHA-256. A moved latest target invalidates an approved default plan. An explicit target stays selected if a newer catalog release appears and the pinned installer metadata is unchanged. APT rechecks installed state, target availability and command arguments. The package manager validates downloads and controls the transaction after handoff.

WinGet integrity error `0x8A150011` is reported separately from transport and general package-manager failures. After a failed transaction the manager re-queries the registered version and reports whether it changed or could not be determined. The structured failure event records the raw return code, normalized Windows HRESULT, target metadata and post-failure observation. WinGet's own diagnostic log retains the actual download digest and size when available. The manager does not retry failed transactions automatically.

## Prototype boundaries

The manager probes absolute executable paths. WinGet post-install verification assumes a versioned KiCad directory under Program Files with both `eeschema.exe` and `kicad-cli.exe`. Distro package verification uses `/usr/bin/kicad-cli` and dpkg's recorded file ownership. Detection covers eSim staging directories, documented overrides, and standard search paths. Relative launcher lookups, custom install locations outside these paths, automatic eSim bootstrap, arbitrary user circuits and HDL fixtures, and GUI workflow execution are outside the prototype. An explicit executable override can point the health report at an existing custom path. Only the built-in standard analog fixture is executed automatically; it does not exercise eSim's GUI, netlister, `d_cosim`, NGHDL, or NgVeri adapters.

## Runtime verification and receipts

`simulation.py` contains exactly one trusted netlist, `voltage-divider-dc-op-v1`: a 3 V source with a 2 kOhm/1 kOhm divider and an operating-point query for `v(out)`. The command accepts no arbitrary circuit or user-supplied simulator arguments. It writes the netlist to a fresh temporary workspace, runs the selected executable as `ngspice -b voltage-divider.cir` with the prepared child environment and a bounded timeout, and captures stdout/stderr. Verification requires exit code 0, no `fatal`/`error` line, and a numerically parsed `v(out)` within `1e-6` of the expected 1.0 V. The temporary directory is removed after the run.

`verification.py` stores the result in `verification.json` next to the manager settings. A receipt is written for both success and failure so health cannot mistake an older success for the current state. `check()` requires a successful receipt, the same circuit identifier, the same canonical executable path, a matching current executable SHA-256, and a matching reported tool version. Changing the binary, replacing it with a different build, or switching versions invalidates the claim without deleting the evidence. `doctor` exposes the runtime classification separately from workflow wiring; if the process has not exported `ESIM_NGSPICE`, the analog workflow remains `unverified` even when the isolated runtime receipt is valid. This distinction prevents an isolated simulator run from being reported as proof that eSim itself launched successfully.

## Portable Windows archive

The Ngspice 47 catalog entry links the official SourceForge `.7z` and pins the SHA-256 from the moderated Chocolatey package that embeds the upstream archive. That independently hosted package is the checksum authority for this entry. The manager uses the upstream URL and restricts redirects to HTTPS SourceForge hosts. A future catalog entry without reviewed integrity evidence cannot download. Catalog updates require reviewing the exact archive and its evidence. [Ngspice Windows releases](https://ngspice.sourceforge.io/download.html), [Chocolatey package verification](https://community.chocolatey.org/packages/ngspice/47.0.0)

On approval, the manager rechecks the plan, downloads with a size bound, and checks SHA-256 before opening the archive. The project-local `py7zr` decoder validates member metadata and decodes regular file contents into bounded memory buffers. The manager constructs an intermediate tar from those buffers, then validates entry types and path segments before writing each file beneath the staging prefix. Links, device names, alternate data stream syntax, path traversal and duplicate destinations are rejected. The staged console executable must report the expected version before a same-volume directory rename publishes the installation. The receipt records the archive hash and every installed file hash for consistency checks. It is stored under the user's account alongside the files.

The previous Windows libarchive converter crashed on the authentic Ngspice 47 archive with `0xC0000005`, although a small archive produced by Windows tar passed its test. The project now pins `py7zr==1.1.4` in `requirements.txt`. The actual upstream archive was decoded and used to complete the approved installation and analog smoke test.

Managed Ngspice is discovered after the eSim-specific override, configuration and launcher paths. The report identifies it as a stock analog tool and explains how to point eSim at the console executable. The per-user store lives outside the eSim checkout. A broken receipt or modified file blocks reuse or replacement of that version until the directory is reviewed. Portable updates report the reviewed catalog version. The transaction does not change permanent environment settings.
